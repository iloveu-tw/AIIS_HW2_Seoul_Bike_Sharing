## 2. 已確認的研究口徑

1. 課程 `10 < 特徵數 < 30` 依使用者後續更正，用於檢查資料集 **One-Hot 後的總候選模型欄位數**，不是最佳入模 `k`。Seoul Bike 的 14 個候選模型欄位符合條件；教授原文未明示編碼計數單位。
2. 使用者確認下一小時任務是在 `t` 已知當下天氣與營運狀態的情境下預測 `t+1`；不得把 `t+1` 的實測值放進輸入。P1 仍須逐欄寫下取得時點及條件。
3. 原始候選欄位 12 個、現有 One-Hot 方案展開後 14 個模型欄位；最佳入模 `k` 可為 1～14 中演算法實際產生並驗證的值。小於 11 的組合不因課程總特徵數條件而被排除。
4. 使用者確認保留停駛時段作為正式目標的一部分，另列營運日成績；下一小時任務的分層以 `t+1` 目標時段的營運標記判定，但模型只能使用 `t` 時點已知資訊。

## 3. 正式實作需要處理的差異

| 項目 | 試跑觀察 | 正式做法 |
|---|---|---|
| 最佳特徵數 | 探索 RFE 路徑的最低驗證 RMSE 出現在當小時 `k=5`、下一小時 `k=6` | 兩者在總候選 14 欄的題目下均是有效候選；正式推薦仍須由正式重跑的外層驗證決定 |
| LassoCV 與路徑 | Lasso 路徑僅有部分 `k` 點；獨立檢查的完整訓練集 `LassoCV` 選到 `k=14` | 路徑圖與交叉驗證後的 Lasso 最終選擇須分別命名；不得用路徑分數冒充正式選擇分數 |
| RFECV 與 RFE | 完整訓練集 RFECV 選到當小時 `k=5`、下一小時 `k=6`；RFE 路徑涵蓋更多 `k` 點 | 兩者都可展示，但須分開標示 RFECV 最終選擇與 RFE 逐 `k` 探索，不得混用分數 |
| 交叉驗證 | 探索程式的 LassoCV 內層交叉驗證前先對整個外層訓練折做標準化 | 正式程式需讓內層每個訓練折自行擬合標準化器，並以一致的外層時間折比較方案，避免驗證資訊洩漏 |
| 測試集 | 試跑為選題比較多種方法，已查看最後 20% 時段的各方法測試分數 | 正式評估須先用訓練區間驗證固定推薦，再檢視留出期；須揭露它曾在選題階段被看過，不能稱為完全盲測或未接觸的獨立證據，也不得依其結果重選 |
| 結論 | 停駛日全部零租借、模型會出現負預測，且時間折表現波動 | 網站與報告應區分整體／營運日、列出負預測比例與各折分數，說明線性模型限制 |

正式比較應先定義單純的預測基準（建議訓練區間目標平均值），與「全部特徵 LinearRegression」分開：前者回答線性模型是否比簡單預測好，後者回答特徵選擇是否比全特徵好。這項基準可於 P1 寫成決策，無須改變已選的四個特徵方案。

## 4. 網站與交付前置檢查

- GitHub Pages 是靜態託管；官方成果由 Python／GitHub Actions 產生後發布。自訂 CSV 的即時計算需在瀏覽器執行。Pyodide 官方套件清單含 pandas 與 scikit-learn，且官方文件提供 Web Worker 用法；但本機 scikit-learn 1.9.0 與目前 Pyodide stable 所列 1.8.0 不同，須在開發初期固定相容版本並做相同小資料的輸出對照。[套件清單](https://pyodide.org/en/stable/usage/packages-in-pyodide.html)、[Web Worker](https://pyodide.org/en/stable/usage/webworker.html)。
- 尚未實測瀏覽器下載套件、載入本機／網址 CSV、CORS、記憶體及完整選模耗時；加分 2 應先做一個非 Seoul Bike 的小 CSV 垂直測試，再擴充圖表與介面。
- `docs/spec.md` 是本次重規劃的準據；`docs/PROJECT_RULES.md`、`docs/PROJECT_PLAN.md`、README 與 P0 交接文件含舊版口徑，正式開發時需標記其歷史性並更新對外入口，避免混用「原始／編碼後均 12～29」與新口徑。
- `backups/`、`__pycache__/`、暫存檔不可進入公開儲存庫。原始 CSV 是否公開上傳，須先核對來源授權與引用；即使不公開原檔，正式分析仍須提供可重現的取得方式及雜湊驗證。
