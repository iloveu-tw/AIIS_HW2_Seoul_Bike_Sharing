# 專案規則 — Seoul Bike Sharing Project

## 研究與執行原則
1. HW2 教授明文要求：Kaggle 多元線性迴歸題目，特徵數 >10 且 <30；我們另採保守條件：**選用原始特徵數、One-Hot 後模型欄位數均為 12～29**。此為專案標準，不應宣稱教授明文要求編碼後維度。
2. 以 CRISP-DM 六階段（P1～P6）執行，P0 為額外的來源及可行性驗證。各階段說明目的、流程、驗證標準後才提供操作或程式。
3. 原始資料 `data/raw/SeoulBikeData.csv` 禁止覆寫；下載 ID、Version、SHA-256 必須記錄。所有資料轉換存於 `data/processed/`，階段結果寫入 `results/Px/`。
4. Python 使用有意義的繁體中文註解；維持最小必要程式與既有風格，不任意重構。
5. 每一階段需具備可重現的輸出：檢查報告、統計資料、圖表、稽核／執行紀錄，以及工作日誌和交接更新；不可只有 Terminal 輸出。
6. 先切分再在訓練資料上擬合編碼器／標準化器；不得讓測試集資訊滲入訓練。時間資料預設以**依日期及小時排序的 80/20 時序切分**進行評估，正式 P3 再確認。
7. `Functioning Day` 只有在預測當時可事先得知營運狀態的研究情境下才可使用。氣象欄位若用於真正未來預報，也須改用預測時可取得的資料；P1 須明確說明。
8. 不以任意 R²、MAE、RMSE 門檻作教授強制規定；比較 Baseline 並如實呈現模型成效。
9. Kaggle 頁面顯示 Database/Contents 分別使用對應開放資料庫授權標籤；資料重製、公開分享前再次核對具體條款，並保留來源註記。
10. 管理文件存放 `docs/worklog/`，每階段結束更新 PROGRESS、HANDOFF、TODO 與當日日期檔；若已有內容先合併，不能直接覆寫。
