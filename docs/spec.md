## 1. 目標與成功標準

以 Kaggle Seoul Bike Sharing 資料，在 CRISP-DM 六階段下完成兩個**多元線性迴歸**預測任務，比較特徵選擇方案，產出可重現的圖表、報表與訓練結論，最後以 GitHub Pages 提供互動展示。

1. 同一份 Seoul Bike 資料能支援兩個已定義的租借量預測任務。
2. 單一 Python 主程式按 CRISP-DM 階段執行，程式註解與輸出標示階段名稱。
3. 每個任務均有全特徵基準組與候選特徵選擇方案；所選特徵數由計算與驗證決定。
4. GitHub 儲存庫保存正式執行產生的圖表、報表、設定與結論；Pages 網站可切換任務及方案。
5. 訪客可上傳 CSV 或提供可公開讀取的 CSV 網址，在瀏覽器重新計算回歸結果。
6. GitHub README 提供 Live Demo 與網站實際完整截圖區。
7. 最終將已驗證的專案流程整理為可重複使用的 Codex skill，供日後對其他合格的表格型迴歸資料集執行同類分析與網站交付。
8. 完工後使用 Archify 繪製與實際程式、成果及網站一致的 CRISP-DM 專案流程圖，供 README 與網站說明引用。

**學習主軸**：用同一個多元線性迴歸模型比較「放入多少個特徵」與「具體放入哪一組特徵」對未見資料預測誤差的影響，並能解釋為何增加特徵不保證改善測試表現。報告須展示模型方程式中的截距與係數、特徵條件式解讀、選擇方法差異，以及結果可成立的資料與時間範圍。

## 3. 兩個預測任務

| 項目 | Problem 1：當小時需求 | Problem 2：下一小時需求 |
|---|---|---|
| 研究問題 | 在當小時氣象與營運資訊已可得、租借量尚未揭露的分析情境下，估計該小時租借量 | 使用時刻 `t` 已取得的資料，預測 `t+1` 小時租借量 |
| 目標 | `Rented Bike Count` 於 `t` | 將 `Rented Bike Count` 依連續時間位移一小時形成 `target_next_hour` |
| 輸入原則 | 候選欄位須在該任務預測時點可取得 | 僅能使用 `t` 時點已知欄位；不得使用 `t+1` 的實測天氣、營運狀態或租借量 |
| 資料檢查 | 日期與小時排序、欄位品質 | 先檢查相鄰列是否確為連續一小時；跨缺口的配對不可使用，最後一筆無下一小時目標須排除 |

兩個任務仍屬同一 Seoul Bike 題目，並以相同的多元線性迴歸框架分析。使用者確認 Problem 2 的情境為：在 `t` 時點已知當下實測氣象與營運狀態，使用 `t` 的候選欄位預測 `t+1`；不使用 `t+1` 的實測資料，亦不預設把 `t` 的租借量加入輸入。P1 須記錄這是條件式預測情境，並逐欄確認 `t` 時點可得性；若實際應用不符合此前提，須排除對應欄位並重新核算特徵數。

正式目標保留 `Functioning Day = No` 的停駛時段；整體評估之外，另列**營運日資料的成績**，避免停駛時段的零租借量掩蓋一般租借需求的預測誤差。Problem 2 的分層應依目標所屬的 `t+1` 時段標記，不把該時段營運狀態作為模型輸入。

## 4. 特徵選擇與模型比較

正式比較四個方案：

| 方案 | 選擇器 | 最終回歸模型 |
|---|---|---|
| A | 全部合格特徵，作為基準 | `LinearRegression` |
| B | `SelectKBest(f_regression)` | `LinearRegression` |
| C | Lasso 交叉驗證選擇非零係數特徵；以 `GridSearchCV(Pipeline(StandardScaler, Lasso))` 實作內層無尺度洩漏的 LassoCV 流程 | `LinearRegression` |
| D | `RFECV` | `LinearRegression` |

- 選擇器、缺值處理、編碼與尺度轉換只在訓練資料內擬合，並置於可重現的分析流程中；測試資料不得參與挑選特徵數或調整參數。
- 依時間排序保留最後 20% 作一次性測試集；前 80% 的特徵與參數選擇使用時序交叉驗證。Problem 2 以**目標所屬時間**安排切分，檢查跨邊界位移是否造成洩漏。
- 主要選擇依據為訓練區間的驗證 RMSE；同等表現時優先較少特徵。另報告 MAE、R² 與測試集結果。不得把多次查看測試集後挑出的最佳方案稱為獨立驗證。
- 前期選題推演已查看最後 20% 時段的探索性測試分數，因此正式報告必須揭露這段資料**並非完全盲測**。正式選擇規則與候選先在訓練區間固定，再做最終留出期評估；不得把同一留出期包裝成首次接觸的獨立證據，也不得依其結果重選。
- 所有方案使用相同的外層時間驗證切分與評分口徑，記錄各折 RMSE／R² 並明示圖上採用的彙總方法。「同等表現」的數值判準須在查看測試集前固定；推薦稱為**已評估候選中的最佳**，不能宣稱已窮舉所有特徵組合。
- 題目的**總候選特徵數**需符合課程限制；特徵數曲線與正式推薦可使用 `1 ≤ k ≤ 14` 中演算法實際產生的組合，不因最佳 `k` 小於 11 而排除。Lasso 或 RFECV 實際選出的數量與組合應如實呈現，不偽造曲線上不存在的點。
- 目前只有 12 個原始候選特徵，特徵數限制可能使正式可比較的子集很少。網站須同時顯示原始欄位數、編碼後維度和實際入模數，避免混淆。
- 橫軸 `k` 指 One-Hot 後**該組合實際入模**的模型欄位數，與用來檢查題目資格的**總候選模型欄位數 14**分開標示；原始欄位、語意特徵群組與模型欄位不混稱。選擇器在展開後欄位層級工作，結果需對照回原始欄位；類別欄位可能只選到部分虛擬變數，須明示其含義與計數方式。
- 圖上的交叉驗證分數由各時間折的訓練／驗證過程產生；不同折可能選出不同組合。表格所列完整特徵組合須標示為「以完整訓練區間重新擬合後的選擇結果」，不得暗示每一折都用了完全相同的欄位。報告另記錄各折分數與入選頻率，供檢查選擇穩定性。
- A 是全特徵單一基準點；B 可按 `k` 比較；C 與 D 只展示演算法實際產生並經相同外層時間驗證評估的特徵數。調參或選擇器內層交叉驗證須留在外層訓練折內，避免圖上分數偏樂觀。
- `SelectKBest(f_regression)` 逐欄評分，未直接評估欄位間共同作用；Lasso 選擇前須在每個訓練折內做尺度處理；RFECV 依回歸模型遞迴刪減。三者各代表不同的選擇思路，網站需用白話說明，且不可把方法選到的欄位解讀成因果因素。
- 網站可簡稱 C 為「Lasso CV」，但方法說明與程式紀錄須列出實際使用的 `GridSearchCV` 與 `Pipeline`，不得宣稱直接呼叫了 `LassoCV` 類別。逐 `k` 的 Lasso path 只是探索曲線，不代表該交叉驗證選擇器的最終分數。

## 5. CRISP-DM 單一主程式

專案根目錄的 `main.py` 是唯一的正式 Python 分析程式；六階段以明確函式與註解依序標示，並輸出階段結果。命令列執行 `python main.py` 完成官方資料的 P1～P6 分析與網站資料產生；瀏覽器端透過 Pyodide 載入同一檔案並呼叫其中可重用的資料檢查、前處理、選擇、訓練與評估函式。網頁 JavaScript 只負責載入資料、呼叫 Python 與繪製互動介面，不另寫一套不同的模型算法。既有 P0 腳本保留作歷史來源驗證，不是第二套正式訓練程式。

| 階段 | 程式與人工工作 | 必要產出／驗證 |
|---|---|---|
| P1 Business Understanding | 記錄兩任務、預測時點、資料可得性、基準與評估目的 | 任務定義；人工確認輸入欄位可得性 |
| P2 Data Understanding | 統計、分布、時序、零租借、欄位關係與品質檢查 | EDA 表與圖；資料筆數及異常記錄 |
| P3 Data Preparation | 建立下一小時目標、切分、訓練內編碼與缺值處理 | 切分與轉換紀錄；洩漏檢查；特徵數核對 |
| P4 Modeling | 執行 A～D 方案，選擇特徵數與參數 | 各方案所選欄位、驗證分數、模型設定 |
| P5 Evaluation | 一次性測試、殘差與基準比較，生成結論 | 指標、圖表、逐任務結論及限制 |
| P6 Deployment | 建立網站資料包，供 GitHub Pages 發布；完工後整理 Archify 流程圖 | 網站資料、Live Demo、截圖、流程圖與部署驗證 |

程式執行應記錄資料來源、版本或雜湊、時間、環境版本、任務設定、特徵清單、切分方式與隨機種子。人工研究判斷不能由程式自動宣稱已完成。

## 6. 結果、圖表與訓練結論

每個 Problem 必須產生下述特徵選擇比較區、對應資料表、訓練結論及可追溯的 Markdown／JSON 報告。數值與圖表須由當次程式結果產生，不硬編範例值。

**網站必備的特徵選擇比較區**：

1. **每個特徵選擇演算法都有一組詳細畫面**：上方並排兩張圖，分別為「特徵數 vs. 驗證 RMSE（越低越好）」及「特徵數 vs. 驗證 R²（越高越好）」；下方緊接同一演算法的逐列結果表。切換演算法時，兩張圖與表格一起更新。這是使用者提供範例圖表與表格的核心版型。
2. 兩圖使用相同的整數特徵數作橫軸；表格每列對應一個實際算出的特徵數，至少列出**特徵數、完整訓練區間重新擬合後的 Selected Features 清單、外層時間驗證 RMSE、外層時間驗證 R²**，並可查看各折分數及入選頻率。滑過或點選圖上資料點時，同步醒目標示表格對應列；表格選列也要回應圖上的點。
3. 每個演算法標示其驗證最佳列，再依訓練區間的時序驗證 RMSE，在所有已評估候選中選出**整體推薦的演算法、特徵數和特徵組合**；另設跨演算法摘要供比較。RFECV 的 5／6 欄若是正式重跑後的結果，也可成為推薦候選。R² 同時呈現供判讀，測試集只用於評估事先選出的方案，不用來反覆重選。
4. 圖表與表格區分「已實際計算的逐 `k` 路徑」及「LassoCV／RFECV 交叉驗證後的最終選擇」，而非依 `k ≥ 11` 區分合規性。演算法若未產生某個特徵數的有效結果，不補畫、不內插，也不虛構對應特徵清單；範例圖中的特徵名稱、分數及最佳點不可沿用為 Seoul Bike 的實測結果。

其他網站圖表（例如資料分布、實際值對預測值、殘差分析）目前是設計建議，待與使用者討論後決定是否列為網站必備；研究報告仍需提供足以支持訓練結論的評估證據。建議至少保留實際值對預測值、殘差對預測值及殘差隨時間變化，檢查系統性偏差、離群時段與時序相關。

網站中的「訓練結論」區，隨 Problem 與方案切換，包含：

1. 驗證階段選出的推薦方案、特徵數與完整特徵名稱。
2. 留出期 MAE、RMSE、R²，以及相對全特徵基準組的差異；同時列出整體與營運日分層成績。
3. 殘差檢查所見的主要誤差型態與適用範圍；區分程式算得的數值與人工解讀。
4. 限制與未解決問題，例如預測時點的氣象資訊、停駛日、線性關係不足或時間漂移。
5. 以選定模型的截距與係數寫出可讀方程式，註明原始單位、類別參考組及標準化方式；相關特徵可能使個別係數不穩定，不能把相關性直接解讀為因果。

推薦方案只代表此資料、此切分與此驗證規則下的結果，不宣稱通用最優。自訂資料集以相同欄位格式產生當次摘要；若總候選特徵數不符合作業限制，須說明不符合課程題目條件，但可依資料能力顯示探索結果；若分析失敗或無有效組合，顯示原因而不生成結論。

## 7. 網站模式與 GitHub 執行分工

| 模式 | 計算位置 | 使用者看到的行為 |
|---|---|---|
| 官方兩任務 | 本機開發與 GitHub Actions 執行 Python；成果發布到 Pages | 切換 Problem 或方案時，即時切換已驗證的圖表、報表與結論 |
| 自訂 CSV 檔案／網址 | 瀏覽器 Pyodide 執行同一份 Python 分析核心，放在 Web Worker | 選目標欄、啟動計算、查看進度與當次結果 |

GitHub Pages 不執行伺服器端 Python。GitHub Actions 可在正式資料或程式更新後重跑，產出／保存圖表、報表與網站資料，再部署 Pages；Actions 執行與部署有等待時間，不能當成訪客點擊後的即時計算。自訂網址須直接回傳 CSV 且允許瀏覽器跨來源讀取；本機檔案上傳可作為替代入口。自訂資料不自動推送至公開儲存庫。

Actions 使用的正式原始資料須有可重現的取得方式，執行時核對版本與 SHA-256；若需憑證，只能使用 GitHub Actions Secrets，不得寫進網頁或儲存庫。正式結果與網站資料應由同一次成功執行產生，避免網站展示舊版圖表搭配新版指標。

自訂模式第一版限定**表格型 CSV、連續數值目標、多元線性迴歸**。網站須讓使用者選目標欄與可用特徵，檢查筆數、欄位型態、缺值、類別展開後維度及檔案大小。是否採時序切分須依資料與使用者指定時間欄決定；不能把 Seoul Bike 的時間規則盲套所有資料。瀏覽器可接受的檔案大小與運算時間上限以實測後確定。

## 8. 網站內容與視覺設計

首頁最上方須先有醒目的 **Seoul Bike Sharing 多元線性迴歸與特徵選擇**主題區，讓訪客在操作前看懂資料集、預測目標及本作業要比較的「特徵數與特徵組合」。主題下方以易讀的概覽卡呈現資料來源、資料筆數、總欄位數、原始候選特徵數、編碼後模型維度、預測任務數及特徵選擇方案數；必要時註明目標單位與資料時間範圍。官方資料的 P0 已知值可作初始說明，但正式網站須從已驗證的成果資料包讀取，且清楚區分「原始欄位數」「候選特徵數」與「入模特徵數」，不得把示意圖的數字當作訓練結果。切換到自訂 CSV 後，概覽卡改顯示當次載入資料的實際統計，不沿用 Seoul Bike 數值；尚未計算的項目顯示待計算狀態。

主題與資料概覽之後，主要畫面依序為：任務選單、資料來源與方法說明、方案選單、核心指標卡、互動圖表與對應特徵組合表、訓練結論、限制與資料來源。另設自訂資料區，提供 CSV URL 與檔案上傳。Problem 選單切換預測任務；方案選單切換特徵選擇方法，兩者語意不得混用。

視覺方向參考 iOS 26 Liquid Glass 的互動感：深藍／靛紫背景之上，控制項與容器呈現半透明層次、隨指標或觸控位置變化的局部高光、輕微折射感與按壓回饋；切換選項時以短暫平滑過渡維持內容脈絡。效果應集中在介面層，不扭曲圖表線條或數值。圖表區維持高對比、清楚軸標和足夠留白；提供手機觸控對應行為及系統「減少動態效果」支援。

兩項加分功能以同一套深色玻璃介面中的不同色調標示：**加分 1（兩個 Problem 切換）用薄荷綠；加分 2（自訂 CSV 檔案／網址）用靛紫／淡紫色**。對應的功能按鈕即使未選中也保留各自識別色，選中時提高亮度並顯示 `+1`／`+2` 文字標籤，不只依靠顏色。RMSE／R² 圖表及數值的語意色保持一致，避免資料模式切換後改變讀圖規則。自訂模式未完成時須明示介面預覽與停用計算，不用配色暗示功能已可執行。

**風格參考必須服務多元線性迴歸**：挑選機器學習互動網站時，優先參考能清楚呈現連續數值預測、特徵數與組合、RMSE／R²、實際值和預測值差異的版面與互動。兩張特徵數曲線、對應表格及訓練結論是視覺主角；玻璃效果不得降低線條、數字、圖例或表格的可讀性。分類問題專用的混淆矩陣、ROC／準確率等，不套用為本作業的主要成果。

正式視覺定稿前，整理**十個知名或高使用量的機器學習互動網站**作參考清單，記錄網址、查閱日期、可借鏡的圖表／互動、對本作業迴歸分析的適配性，以及採用或不採用的理由；優先比較能展示特徵選擇、回歸指標、實際值與預測值的案例。若稱為「最熱門前十名」，須先說明排行指標與可查證來源，不以主觀印象宣稱排名。參考清單屬設計研究，最終採用的版型仍須以本節的教學目標、可讀性與使用者確認的 Liquid Glass 風格為準。

優先互動：兩方案並排比較；滑過資料點時同步標示特徵數、指標與對應特徵；切換時平滑更新圖表、結論與指標卡；自訂計算有清楚的載入、進度和錯誤狀態。輸入條件的即時試算屬後續候選，須另驗證可用輸入與模型推論一致性。

## 11. 階段驗收與待確認事項

1. **規格確認** → 驗證：兩個預測時點、可用欄位、特徵計數口徑及加分項解讀已記錄。
2. **主程式與資料處理** → 驗證：原始檔雜湊不變；兩任務無時間洩漏，六階段輸出可重現。
3. **方案比較與結論** → 驗證：四方案具備真實特徵清單、驗證／測試指標、圖表及有根據的結論。
4. **正式成果與網站** → 驗證：首頁主題與資料概覽可清楚區分各種特徵數，官方／自訂資料切換後數值正確；十個網站的設計參考清單與取捨有據；GitHub 圖表及報表清單完整；Pages 互動、結論、Live Demo 與完整截圖均可用；README 每張截圖在儲存庫有可下載的對應原檔與索引，供繳交作業使用。
5. **自訂資料模式** → 驗證：至少一份非 Seoul Bike 的合格 CSV 能在瀏覽器重新分析；錯誤格式有明確提示。
6. **Skill 交付** → 驗證：skill 結構與內容通過檢查；以一份非 Seoul Bike 的合格回歸資料進行實際演練，確認能遵循同一流程並產出可追溯結果。
7. **Archify 流程圖** → 驗證：圖中的資料來源、P1～P6、兩任務分流、特徵選擇與評估、正式／自訂網站計算路徑及交付物，均可對照已完成程式與網站；來源可重建、版面可閱讀並通過 Archify 驗證。
